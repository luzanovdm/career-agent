# Host and platform capabilities

A host must support safe local file extraction and process execution to run the installed application. Use its available hashing/extraction tools to verify a complete platform archive before executing bundled Python. Global Python, Node, a hosted service or remote MCP is not a runtime prerequisite. When capabilities are absent, provide an honest structured handoff; do not claim local persistence or silently run source/global helpers.

The builder pins Python-build-standalone provenance per platform. Only the macOS arm64 target has current native installed acceptance evidence. Its declared macOS minimum is not tested on that older OS. macOS x86_64, Linux x86_64 and Windows manifests are declarations requiring target testing. Windows private process control is explicitly unsupported in the current implementation and cannot be certified from a Unix test.

Native questionnaires, file reading, browser research and provider access are optional host capabilities. Use the user's language and a concise text fallback when native input is unavailable. The runtime contains no browser automation, model provider SDK, research worker or sender. Access to a connector does not grant research/send authority. Complex UI prompts are pasted into a separately authorized agent and resolved with installed state.

No personal/global skill is installed by source development. The full platform bundle contains its installed skill and exact runtime, while host activation/loading follows that host's supported mechanism. A source Markdown view alone is not proof of skill activation. New-chat behavioral tests must load the installed instructions and actual fixture inputs without expected answers or coached repairs.
