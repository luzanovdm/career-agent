# Employee contacts and email diagnostics

Use this when choosing a personal contact/channel, preparing email outreach, checking an active email batch, or reviewing delivery problems. Research still requires the current [discovery](discovery.md) start/scope and stops immediately on pause. Sending always needs its own valid permission; the helpers never send. Work in the user's language and reuse valid answers. The detailed [design](outreach-design.md) explains the decisions; [state format](state-format.md#outreach-owner) owns record fields.

## Executable path

When bundled helpers can run, use `scripts/career_outreach.py`; do not replace these checks with prose, generic `put`, handwritten state changes or a second spreadsheet ledger. The existing state validator invokes the same invariants; generic writes to owned collections are refused. Read the schema when preparing structured requests, not all references at every invocation. Every command returns structured JSON, with `sends_performed: 0` and explicit reasons. Ordinary users do not run scripts or edit JSON.

1. **Start/session/batch:** read `summary STATE --at TIME` (also included by `career_state.py stats`). Its cadence results say which representative variant is due. No current representative payload means inspection/testing remains unknown. Reuse the private workspace; missing diagnostics warn without blocking independent search/preparation. No scheduler is implemented; only arrange a real supported authorized schedule when explicitly requested, otherwise check next session and say nothing runs while closed.
2. **Find the relevant owner:** use vacancy/team/company pages, LinkedIn/professional profiles, engineering posts/talks or authorized prior correspondence. Optional professional data-provider adapters need supported tools and appropriate scope; no purchases by default. Choose by evidenced relevance, not seniority or an exhaustive mandatory order. Stop once a sufficiently qualified usable route exists; retain ordinary form/application alternatives.
3. **Save/assess:** `contact STATE CONTACT.json --at TIME --expected-revision N --reason TEXT`, then `contact-check STATE --id CONTACT_ID --opportunity-id ROLE_ID --at TIME`. Preserve source URL, dated observation, relevance and five separate confidence axes. Named person, role inbox, general inbox and inferred address stay distinct. Current affiliation needs a dated source and recheck interval. Published professional address does not establish mailbox validity; DNS/MX or a guessed pattern never does. Use another evidenced route after a hard failure, not enumeration. Shared person/channel identity spans roles; namesakes stay distinct and aliases need evidence.
4. **Prepare the actual outgoing payload:** keep mode (`vacancy`, `company_problem`, `paid_project`) separate from purpose (`application`, `cold_introduction`, `follow_up`). Show source → role/problem → contact rationale → message. Expected direct applications include the CV; first cold introductions default to short text without attachments/links, with intentional exceptions reviewed. Preserve supported metrics/accomplishments despite heuristic word flags. `inspect PAYLOAD.eml VARIANT.json` checks actual plain/HTML, headers, attachment metadata, links, hidden content/tracking. URL destinations are unfetched until a supported host tool checks them; 999/403 bot denial is inconclusive.
5. **Persist intent:** `prepare STATE REQUEST.json --payload PAYLOAD.eml --variant VARIANT.json --at TIME --expected-revision N`, then `check STATE --id ACTION_ID --at TIME`. Use one stable idempotency key for one intended action. The request includes actual data classes (`message_headers`, `message_body`, plus `attachments` when present), source IDs, reason and exact role/contact or a separately typed diagnostic. Preparation records a draft, never a send. `check` enforces contact evidence, suppression, prior forms/history and coordination. A prior form blocks duplicate reapplication but permits a justified personal follow-up acknowledging it. No simultaneous multi-person blast; switching after contact needs documented reassignment/failure or approved waiting policy. Honor opt-outs at the expressed scope; employer rejection is not a permanent company/person ban.
6. **Diagnose when due:** `due STATE --variant-sha256 HASH --at TIME`. Default: before the first active email batch, after material sender/provider/delivery/template/stable-link/attachment-generation changes, then every seven active-campaign days (configurable). Exact bytes and representative variant hashes are separate. Do not retest variable candidate/vacancy text. Compare actual structure and declared revisions; update revisions for substantive generator changes even when MIME shape stays the same. `local_only` forbids diagnostic disclosure. Local inspection cannot establish receiver-side SPF/DKIM/DMARC or SpamAssassin results.
7. **Permission and handoff:** `grant STATE GRANT.json --at TIME --expected-revision N --user-confirmed` records an actual decision; reuse existing `check.permission_ids` without asking again. Grants bind recipient/service/sender/provider/data/purpose and exact payload, or an explicitly standing diagnostic variant with validity/usage limits. One-time approval never becomes standing. Employer outreach permissions remain exact; employer legal agreements still follow [packets](packets.md). `revoke STATE --id GRANT_ID --reason TEXT --at TIME --expected-revision N --user-confirmed` records withdrawal. `transition` to ready/dispatching takes a structured request; dispatching also requires `--payload PAYLOAD.eml` readback. Only a **new** response with `dispatch_claimed: true` permits one separately authorized supported host adapter handoff. A replay returns false. This project supplies no adapter and no external send. Do not claim exactly-once behavior from a provider without idempotency.
8. **Reconcile:** record host/user/provider evidence through `transition` to sent/failed/uncertain. Unknown acceptance, timeout or lost API response remains uncertain; dispatching after a crash is unresolved, never timer-retryable. Only evidence of no send permits failed; uncertain resolution needs explicit provider/history reconciliation. A known refusal/quota may set `retry_after`; it does not invalidate an employer contact. A fresh attempt after a proved non-send may reuse still-valid exact permission. Before follow-up, use a fresh scoped inbox check or user-attested read-only check; a late reply makes that follow-up obsolete, so cancel it without auto-generating another reply.
9. **Receiver result and reporting:** `receiver-report STATE REPORT.json --id ACTION_ID --at TIME --expected-revision N` binds real receiving evidence to the exact test and recipient. Distinguish hard/temporary bounce, missing mailbox/domain, API quota, actual spam rejection/auth failure and unknown. Store numeric SpamAssassin score/rules/threshold as heuristic only, never probability or guarantee. No receiver report means unknown. Unsent diagnostics may record blocked/skipped/unknown local status; this cancels the unsent intent and never supplies passing receiver evidence. Authentication/systematic spam rejection pauses affected delivery only. Hard bounce creates endpoint suppression retained in state/handoff; `suppress` also records actual scoped opt-outs. Diagnostics never enter application attempts/counts/follow-up triggers. Only a confirmed/reconciled **application** action may link to the existing application-attempt ledger; manual historical mail uses history import, without invented delivery proof. `audit` exposes unlinked legacy email/contact events requiring reconciliation; it does not rewrite history.

All payloads, grants and reports belong in the confirmed private workspace, outside repository/installed skill. Keep raw outgoing/received messages there only as authorized; canonical state contains metadata and report evidence. Summaries show reason/contact/source/packet/current state/next action; existing XLSX/CSV remain generated views. Without helpers, preserve these visible records and label checks unexecuted; never claim a guarded/verified send. Markdown cannot sandbox arbitrary host tools or direct file edits: enforcement applies to supported commands/adapters, with audit for legacy/unlinked records.

If a legacy v1 contact history fails the new uncertainty/link checks, use `repair-preview STATE --at TIME` or `audit` for a read-only review and state fingerprint. `repair-contact-history STATE REVIEW.json --at TIME --expected-revision N --user-confirmed` accepts only evidence-backed reconciliation of a named sending observation or unresolved quarantine. The request binds state_sha256, event_id, decision and evidence; reconciliation also names uncertain_event_id and resolved_status. Original bytes remain backed up and before/after records are retained. Quarantine preserves the original observation and blocks affected outreach until actual reconciliation; it can later be restored through the same reviewed operation. Do not edit JSON or erase quarantine through generic profile settings. Imported uncertainty can be reconciled through the existing user-confirmed review-update operation reconcile_import_uncertainty, linking history_id to an evidenced exact-role sent/not_sent attempt_id with evidence and at; the original imported observation remains unchanged.
